## 2. The filter, as it actually behaves (audit)

* **Where:** `RegionalAgent.process` → after `ServiceGeneratorAgent` (feasibility screening, demand loops, class screening)
  and before the regional GA and `HubMILP`; its output is also `last_candidate_pool`, the candidate set of the global stage.
  It runs **before** any canonical economics are used: it reads `Service.capacity` and `Service.weekly_cost` only
  (`weekly_cost` = one vessel's weekly hire, `Service` docstring, `service_generator_agent.py`).
* **Logic:** (1) keep if some corridor of the region has both ports on the rotation; (2) keep if `capacity × 0.5 × 150 >
  weekly_cost`; (3) sort by `capacity / (weekly_cost + 1)` and keep the first `max_services`; demand-coherent loops are
  exempt from (2) and (3) and from the cap.
* **Why (2) is a class test:** both operands are properties of the vessel class, not of the rotation. On the WorldSmall fleet:
  Feeder_450 450 × 75 = 33,750 < 35,000 (fails); Feeder_800 60,000 > 56,000; Panamax_1200 90,000 > 77,000; Panamax_2400
  180,000 > 147,000; Post_panamax 315,000 > 245,000; Super_panamax 562,500 > 385,000. The "150 USD/TEU" is not data: the
  Demand file pays **105 – 2,590 USD/TEU, weighted mean 958, 0.5 % of OD pairs below 150**.
* **Why (3) is not economic:** the key is a class constant, so within a class the stable sort keeps generation order and the
  cap truncates the *tail of generation*: from the largest class ratio down — Super_panamax (0.0195), Post_panamax (0.0171),
  Panamax_2400 (0.0163), Panamax_1200 (0.0156), Feeder_800 (0.0143, cut first).
* **Downstream:** nothing re-examines the decision; the regional GA/MILP and the global stage only see survivors.
* **Interaction with Tasks 9/10:** class screening runs *before* the filter. A rotation whose screened class is
  Feeder_450 would be deleted by (2) rather than offered with another class — but in the current defaults this does not
  occur (below).

## 3. Why the cap matters — and why the pool is not the whole story

`legacy` vs `nofilter` (a *superset* of the legacy pool: every corridor-covering candidate, no cap) under HiGHS 600 s:
**9.33 vs 9.38 M** (proven optimal on all 5): the candidates the cap removes are, as a set, worth ≈ nothing *when the
model is allowed to route over the whole pool*. The economic variant has the **same cap** and a pool that is a
**subset** of `nofilter`'s — yet its best incumbents reach **11.48 M**. A subset cannot beat a proven optimum of its
superset in the same model, so the two models must differ, and the only thing that differs is the **path set**
(`src/network/paths.py`): per OD it keeps the **10 fastest** time-feasible paths (direct first, then transfers sorted by
transit time, then port cost) — not the 10 best. Measured on seed 0 (`evidence/tools/path_crowding.py`):

| pool | candidates | valid paths (uncapped) | kept (cap 10) | dropped | ODs at the cap | service-incidences on kept paths: Post_panamax / Feeder_800 / Super_panamax |
|---|---:|---:|---:|---:|---:|---|
| legacy | 1,217 | 80,623 (3,652 direct + 76,971 transfer) | 13,121 | **67,502 (84 %)** | 1,126 | 9,605 / 8,139 / 2,663 |
| economic | 1,166 | 53,086 | 12,326 | 40,760 (77 %) | 1,033 | **5,541 / 11,702** / 1,733 |
| nofilter | 1,274 | 84,024 | 13,260 | 70,764 (84 %) | 1,143 | 9,520 / 8,446 / 2,630 |

The cap discards 77–84 % of all valid paths, 95 % of which are one-transfer connections; in a pool full of large rotations
that call at the same hubs, paths through them are the fastest and fill the ten slots, and the cheap feeder → hub → trunk
connections never reach the model. The economic pool removes the large loss-making rotations and so changes which paths
survive (Feeder_800 path-incidences 8.1 k → 11.7 k, Post_panamax 9.6 k → 5.5 k). The gain is therefore a statement about the
**path cap interacting with the pool**, not about the feeders alone. The obvious "raise the cap" is not a fix by itself: with 30 paths per OD the model has ~35.8 k variables and ~31.6 k paths
(2.0× / 2.4× the cap-10 model) and HiGHS does **not** converge in 600 s (gaps 33 – 88 %; §6). But the value is real: on seed 3
the cap-30 incumbent is **12.40 M, +2.98 M above the proven cap-10 optimum of the same pool** (9.42 M), i.e. the 10-fastest
rule hides at least that much. Cost-aware path *selection* (the best 10, not the fastest 10) keeps the model size and is the
proposed next step; it was not implemented or measured here.

## 4. The change (default `auto`; reversible)

* `src/services/regional_filter.py` — `filter_mode()` (`LINER_REGIONAL_FILTER`: `auto` default | `economic` | `legacy`;
  `auto` = economic while loops or class screening are on, legacy when both are off), `select_economic()` (pure,
  tested), `FilterReport`.
* `RegionalAgent._filter_services` delegates to `_filter_services_economic` when the mode is `economic`; the legacy
  branch is byte-for-byte the previous logic (test `test_legacy_filter_is_unchanged_when_selected`).
* Economics come from the **existing** `ClassScreener.evaluate_class` (hire + fuel at the pinned price + port calls,
  capacity on every leg, transit-time-feasible cargo, best weekly frequency): no second revenue/cost formula.
  An unknown class or an unevaluable rotation gets `None` → ranked last and counted in
  `FilterReport.economics_unavailable` — never zero, never an invented value.
* `network_ledger.assumptions.candidate_generation.regional_filter` records the mode of every run.
* Pool restoration: with the default (`auto`), `LINER_DEMAND_LOOP_BUDGET=0 LINER_CLASS_SCREEN=0` reproduces the baseline candidate
  pool **element by element and in order**, seeds 1–3, all regions (508 / 405 / 499):
  `evidence/comparisons/pool_restoration_switches_off_vs_baseline.md`.
* The production code path reproduces the harness variant exactly: ordered pool hashes equal and profits equal to the
  dollar on 5/5 seeds (`T16prod_cbc` vs `T16_seed*_econ_cap_cbc`).
* What the economic filter changes in the pool (defaults, seeds 1–3): per region 16–69 candidates swap —
  Feeder_800 in, Post/Super-panamax out; the pool size is unchanged
  (`evidence/comparisons/pool_legacy_vs_economic_filter_defaults.md`).

## 10. Limitations

* The controlled experiment bypasses the regional GA/MILP (no hints) — the end-to-end orchestrator gate runs are in the
  final summary.
* The 600 s economic incumbents are not proven optimal (gaps 7 – 20 %); the real value of that pool is higher.
* Stand-alone profit ignores transfer cargo: it is an *ordering signal* for the cap, not a statement of network value
  (several selected economic-pool services have a negative stand-alone profit and a positive network role).
* Five seeds of one generator; CBC at 120 s has seed-to-seed and run-to-run spread of ±0.6 – 0.9 M.
